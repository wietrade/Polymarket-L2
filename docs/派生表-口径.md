# L2 派生表口径（`data/derived/`）

> 生成工具：`tools/l2_derive.py`（★只读原始数据；产物全在 `data/derived/`，不入库）
> 建立日期：2026-09-12。原始数据仍是**唯一真相**，派生层随时可重算。

---

## 0. 为什么要有这层（都有实测数字背书）

原始 `data/<date>/*.jsonl.gz` 是一行一条的原始 WS 帧，**不该重写**，但它有四个坑，
每个消费者（研究脚本、对账脚本）都要重新踩一遍：

| 坑 | 实测量（2026-09-12 全量扫描 3411 文件 / 578 万行，`_manifest.json` 口径） |
|:--|:--|
| 文件名 ≠ 市场 | **1083 个文件里含 >1 个市场**（相邻轮次残留被写进同一文件）|
| 行内时间戳不单调 | **6003 行出现时间回退** ⇒ 不能拿"最后一行"当最新盘口 |
| 有截断文件 | 4 个（重打当天包时该 bar 正在写）⇒ `gzip` 直接 `EOFError` |
| 只有 `asset_id`，没有 UP/DOWN | 本地 `markets.csv` 对新 bar 覆盖不全（抽 40 个 L2 `market` 命中 **0/40**）⇒ 侧别必须单独向 gamma 取 |

另外：`price_change` / `tick_size_change` 在采集端就被丢弃（`recorder_l2_dual.py` 只保留
`book` 与 `last_trade_price`）⇒ **档位级逐笔 order book / 队列位置无法重建**，这是数据边界，
派生层解决不了，也不假装解决。

## 1. 产物布局

```
data/derived/
  bar_tokens.parquet                       L1 侧别映射（condition_id -> up/down token）
  bar_tokens_state.json                    已解析集合（断点续跑用；已解析不再重复抓）
  quotes/day=YYYY-MM-DD/coin=btc/cycle=5m/part-0.parquet     每 book 帧一行（顶档）
  trades/day=YYYY-MM-DD/coin=btc/cycle=5m/part-0.parquet     每 last_trade_price 一行
  marks/day=YYYY-MM-DD/coin=btc/cycle=5m/part-0.parquet      gap/mark 行（秒口径）
  _manifest.json                           计数 / 截断文件 / 未知侧别 / 耗时（复核用）
```

分区是 Hive 风格，DuckDB 直接读：

```sql
SELECT * FROM read_parquet('data/derived/quotes/**/*.parquet')
WHERE day='2026-09-12' AND coin='btc' AND cycle='5m' AND is_primary=1;
```

## 2. 三张表的列口径

### `quotes`（一个 `book` 帧一行）

| 列 | 口径 |
|:--|:--|
| `day` | 分区用的 UTC 日期（= 原始文件所在日目录）|
| `ts_ms` | 帧内 `timestamp` 字段，**ms epoch，UTC**，不做时区转换 |
| `bar_ts` | **文件名**里解析出的 bar 起点（epoch 秒）；见 `is_primary` 说明 |
| `market` | `condition_id`（行内 `market` 字段，权威归因字段）|
| `asset_id` | 该行的 token id（权威归因字段）|
| `side` | `1`=UP、`0`=DOWN、`-1`=未知（gamma 没查到，或 outcomes 不是 ["Up","Down"]）|
| `best_bid` / `best_bid_sz` | `bids[-1]`（**bids 升序**，实测 3411 文件 0 例外）|
| `best_ask` / `best_ask_sz` | `asks[0]`（**asks 降序**，实测 0 例外）|
| `mid` | `(best_bid+best_ask)/2`；任一侧缺失 ⇒ `null` |
| `spread` | `best_ask-best_bid`；任一侧缺失 ⇒ `null`（**不含手续费**）|| `n_bids` / `n_asks` | 档位数（判断"薄盘口"用；p50 约 48 档 / 侧）|
| `book_hash` | 帧内 `hash`（同一快照重复帧可用它去重/检测变化）|
| `slug` | 来源文件名（仅参考，**不可当市场归因**）|
| `is_primary` | `1`=本行 `market` == 该文件的主市场；`0`=相邻轮次残留 |

排序：分区内按 `(asset_id, ts_ms)` 升序 ⇒ **同一 `asset_id` 的最后一行就是最新盘口**
（原始数据里时间戳有回退，这个排序把它修掉了）。

> ⚠️ **bar 末段单侧空盘口是常态，别拿 `mid` 当唯一信号**（2026-09-12 实测 n=190）：
> bar 结束前 2s 的最后一帧里，`mid` 为空占 **99.4%**，`best_bid` 为空 45.0%、`best_ask` 为空 54.4%。
> 原因是临结算时一边在收敛（bid→~1）、另一边没人报价：
> **赢家侧 `best_bid` 100% 非空、p50=0.990；输家侧 `best_bid` 只有 ~60% 非空、p50=0.010**。
> 所以要「末段价格」就用 `best_bid`（取末 60s 内最后一次非空值），不要用 `mid`。

### `trades`（一个 `last_trade_price` 一行）

列同 `quotes` 的公共部分，另有：

| 列 | 口径 |
|:--|:--|
| `taker_side` | 帧内 `side`（`BUY` / `SELL`，**taker 方向**，非 maker）|
| `price` / `size` | 成交价 / 成交量（字符串转 float）|
| `fee_rate_bps` | 帧内费率（bps，整数；updown 实测 `0`）|
| `tx_hash` | 帧内 `transaction_hash`（**不是 `hash`** —— 采集端去重键就用它）|

### `marks`（gap 标记，**单位与上面不同，别混**）

| 列 | 口径 |
|:--|:--|
| `from_ts` / `to_ts` / `lost_s` | **epoch 秒**（采集器的 wall clock），不是 ms |
| `note` | `reconnected` / `unresolved` |
| `slug` / `coin` / `cycle` / `bar_ts` | 同 `quotes` |

注意：mark 行只在"当时有活跃文件句柄"时才写得进去 ⇒ **marks 表不保证覆盖全部缺口**，
它只是采集器自己报告的那部分；判断某个 bar 有没有缺口要看 `quotes` 的时间分布。

## 3. L1 侧别映射口径（`bar_tokens.parquet`）

- 来源：gamma `/markets?condition_ids=<id>&closed=true`，取 `outcomes` 与 `clobTokenIds` 的**同序对应**。
- **必须带 `closed=true`**：不带时按 `condition_id` 查已结束市场返回 `[]`（实测）；反之，
  **当前还没结束的 bar** 用 `closed=true` 查不到 ⇒ 工具会自动去掉 `closed` 再补抓一次。
- `outcome_kind`：`updown`（outcomes 顺序 = ["Up","Down"]）、`updown_rev`（反序）、
  `other:*`（例如 ["Yes","No"] ⇒ 该 market 不是 updown，对应行的 `side` 一律 `-1`）。
- **顺带收下官方结算**：`outcome_prices`（如 `["1", "0"]`）、`winner`（`UP`/`DOWN`；未结算或非二选一则为空）、
  `closed`。这样本地就知道每个 bar 的赢家，不必依赖 `poly_data` 的结算表
  （实测那份 `settlements.parquet` 只更新到 2026-09-06，对我们 09-07 之后的 3355 个 bar **命中 0**）。
- **缓存版本**：字段集变更时 `TOKENS_V` +1 ⇒ 旧缓存自动作废重抓（防「新列静默留空」）。
- 幂等：跑过的不再重复抓（`bar_tokens_state.json` 记已解析集合）；`--force` 才重抓。

## 4. 已知边界（用之前先读）

1. **`price_change` 缺失**：只能看到 `book` 全量快照（间隔 p50 **98ms** / p90 706ms / max 56.8s）
   ⇒ 能做"快照点上的盘口"，不能做档位级逐笔重建、不能算真实队列位置。
2. **bar 覆盖度**：`2026-09-10 08:51 UTC` 之前的 bar 只能信末 ~180s（采集器订阅换代缺陷，
   已修，见 `docs/` 与 repo 记忆）；用老数据前先确认决策时刻是否落在 bar+150s 之后。
3. **截断文件**：重打当天包时正在写的 4 个文件读不全（工具会记账进 `_manifest.json`）；
   下次重打包 + `l2_get.py` 合并解压后会补全，重跑派生层即可。
4. **`is_primary=0` 的行**：`slug` / `bar_ts` 不代表该行自己的市场，只能当"当时在录哪个 bar"的参考。
5. **顶档只有一档**：需要更深档位时自己从原始 gz 读（本层不保留全档，避免体积膨胀数倍）。

## 5. 跑法与自检

```bash
# 离线自检（不联网、不碰真数据，造 fixtures 验 30 项）
python -B tools/l2_derive.py --self-test

# 全流程（L1 抓映射 -> L2 生成派生表 -> 校验），断点续跑
python -B tools/l2_derive.py

# 分步
python -B tools/l2_derive.py --stage tokens
python -B tools/l2_derive.py --stage tables
python -B tools/l2_derive.py --stage verify

# 只处理某几天
python -B tools/l2_derive.py --days 2026-09-12
```

`--stage verify` 做两件事，任何一项不过就非 0 退出：

1. **行数双侧比对**：从原始数据重算 `book` / `last_trade_price` / `gap mark` 的行数，与
   parquet 实际行数逐表比对（唯一真相口径）；
2. **抽样逐字段比对**：随机抽文件，把原始行的顶档/成交字段与 parquet 里的值逐字段比对。

`data/derived/_manifest.json` 记录**本次运行**的时间戳、`stage`、覆盖的 `days`、扫描行数、截断文件清单、坏行数、
含多市场的文件数、各表计数、**side 未知行数**（以及 top10 未解析 `asset_id`）与耗时 —— 复核就从它看起。

### 2026-09-12 首次全量生成的实测结果（可作基线）

| 项 | 值 |
|:--|:--|
| 原始文件 / 行 | 3411 / **5,786,672** |
| quotes / trades / marks | **3,926,121 / 1,860,472 / 79**（与原始逐表行数完全一致）|
| side 未知行 | **0**（3355 个 condition_id 全部解析成功，且全部 `updown`）|
| 截断文件 / 坏行 | 4 / 0 |
| 含多市场的文件 | 1083 |
| 校验② 抽样逐字段 | 320 行，异常 **0** |
| 派生表体积 | 128 MB（parquet+zstd）| 
| 耗时 | 全流程 431s（扫描+解析 ~140s、建表 ~70s、校验 ~120s）|
| 幂等 | 重跑同一天的 8 个分区，md5 全部不变 |

## 6. 独立交叉验证（不靠工具自己的 verify）

用**官方结算价**（gamma `outcomePrices`）当第三方真相，检验侧别映射与顶档数据：

口径（随机抽 200 个 market 的版本 + 全量版本，覆盖 6 天）：
- 对每个 bar，取 `up` token 与 `down` token 在 **bar 结束前 60s 内最后一次非空的 `best_bid`**；
- 判据：`bid_up > bid_dn` ⇒ 预测 UP（赢家 bid→~1，输家 bid 常为空 ⇒ 记 -1）；
- 与官方 `winner`（gamma `outcomePrices`）比对。

**该检查已固化成脚本（只读本地数据、不需要联网）**：

```bash
python -B tools/l2_settle_xcheck.py              # 全部 6 天
python -B tools/l2_settle_xcheck.py --days 2026-09-11 --sample 300
```

结果（全量 3355 个 market → 2351 个 bar 可判，其余因**末段无数据**（覆盖缺口）或窗口内两侧都无 bid 而跳过）：

| 项 | 值 |
|:--|:--|
| 一致率 | **99.83%（2351 条，4 条例外）** |
| 官方 UP 赢 | `bid_up` 非空 100% p50=**0.990**；`bid_dn` 非空 64% p50=0.010 |
| 官方 DOWN 赢 | `bid_dn` 非空 100% p50=**0.990**；`bid_up` 非空 66% p50=0.010 |

⇒ 结论：`clobTokenIds[i]` 与 `outcomes[i]` 的配对**整体无误**（若系统性配反，一致率会接近 0 而非 99.83%）。

**4 条例外（0.17%，未抦掉，逐个列在这）**：全在 `2026-09-09`（3 条）与 `2026-09-10`（1 条），
即**采集器订阅换代缺陷（09-10 08:51 UTC）之前**、覆盖度已知有问题的时段。其中一条典型：
bar `btc-updown-5m-1788972000`（官方 `outcomePrices=["1","0"]` ⇒ UP 赢），但 L2 里
`clobTokenIds[0]` 收敛到 **0.01**、`clobTokenIds[1]` 收敛到 **0.99**。两种解释都能解释这一现象，**尚未定论**：
1. 该 market 在 gamma 里 `outcomes` 与 `clobTokenIds` 的**顺序对不上**（⇒ 这一个 bar 的 up/down 标签是反的）；
2. 结算确实与盘口共识相反（5m/15m 的裁判是 **Chainlink TWAP**，不是最后一口价）。

⚠️ 因此：**若研究结论落在某 1 个 bar 上，会单独核一下它是不是这 4 条之一**；追这份名单：
`python -B tools/l2_settle_xcheck.py | tail` 会把不一致逐条打出来。

> 另注：`poly_data/data/settlements.parquet` 只更新到 **2026-09-06**（对我们的 bar 命中 0/3355），
> 且该文件的 `outcomes`/`outcome_prices` 是**双重编码**的 JSON 字符串（要 `json.loads` 两次）——已不用它。
