# L2 数据与工具（Polymarket updown 5m / 15m）

本仓库既是**采集器源码库**，也是**本地 L2 数据工作区**：把 43 上自研 recorder 采集的原始数据
按天取回本地，配套下载/校验工具，以及"线上正在跑的那份程序"的只读快照。

> 采集器本身的设计、参数、部署与运维见仓库根目录的 [`README.md`](../README.md)。

> 数据红线：`data/` 下的原始数据**勿删**。确需清理请先与负责人确认。
> 代码与数据分开（靠子目录，不靠两个仓库）：源码在仓库根，数据在 `data/`，工具在 `tools/`，线上快照在 `program/`。

## 2. 数据来源与发布链路

```
43 采集：polymarket-l2/recorder_l2_dual.py
        4 条线 = btc/eth × 5m/15m；每条线 2 条独立 WS 订同一市场（双连接热备，
        单条断线由另一条补，gap 归零）→ 去重 → 单文件模型写 gzip
        ↓ 落盘 /www/wwwroot/polymarket-l2/l2_data/<date>/*.jsonl.gz
每天 03:30：cron 跑 tools/l2_pack_publish.sh
        l2_pack.py  按天打包（幂等；**当天的包会随数据增长被同名重打**）
        发布到 8001 的 www/_dl/（支持 HTTP Range 断点续传）
        同时生成 _dl/manifest.json（文件名 + 大小 + mtime + sha256）
        ↓
本地：python tools/l2_get.py     （按清单只补缺的/变化的，校验通过才解压）
```

数据内容：每个 `<date>/<coin>-updown-<cycle>-<epoch>.jsonl.gz` 是该 bar 的
`book`（L2 盘口增量）与 `last_trade`（真实成交）事件流。

## 3. 常用命令

```bash
# 看清单与本地状态（不下载）
python tools/l2_get.py --list

# 补拉所有"已完成"的日包并解压（默认数据根 = ./data）
python tools/l2_get.py

# 并发数（默认 12）：本机到 43 单连接被限速，加大并发能明显提速
python tools/l2_get.py --jobs 24

# 只关心最近 3 天 / 只下不解压
python tools/l2_get.py --days 3
python tools/l2_get.py --no-extract

# 连当天的包也拉（当天还会变，慎用）
python tools/l2_get.py --include-today

# 手工下载单个包（curl -C - 续传）
curl -C - -O http://43.165.167.132:8001/dl/l2_2026-09-08.tar.gz
sha256sum -c l2_2026-09-08.tar.gz.sha256

# 核对本地程序快照是否与 43 运行版一致
bash tools/sync_program.sh --check

# 每 bar 覆盖率：首帧偏移 + 覆盖秒数（判断 recorder 有没有在录 / 某批数据能用在 bar 第几秒之后）
python tools/l2_bar_coverage.py --date 2026-09-10 --by-hour
python tools/l2_bar_coverage.py --date 2026-09-09 --date 2026-09-10 --detail

# 派生层：原始 gz → 可查询表（侧别映射 + 顶档/成交/gap），= 上面那几个坑的现成解法
python -B tools/l2_derive.py --self-test   # 离线自检（不联网、不碰真数据）
python -B tools/l2_derive.py               # 全流程（断点续跑）；口径见 docs/派生表-口径.md
```

## 4. 校验与对账

- **下载后必须看 sha256**：`l2_get.py` 会自动比对，不一致就不解压。
- **不要用"文件存在"判断已下载**：同一天的包会被**同名重打**（例如当天的包先只覆盖到
  某个时刻，凌晨 03:30 变成完整版）。只判存在会永久漏掉后半天的数据。
- 程序快照对账：`program/VERSIONS.txt` 记录每个文件的 sha256，
  在 `program/` 下执行 `sha256sum -c VERSIONS.txt` 即可验证。

### 中断/休眠怎么办

- **电脑休眠会把本地下载冻住**（2026-09-11 实测：休眠后日志停在原地、进程也被清掉）；
  服务器侧不受影响（实盘、采录、打包 cron 照跑）。
- 醒来后**直接重跑 `python tools/l2_get.py` 即可**：
  已下完的包按 sha256 判为最新会跳过，下到一半的按分片续传（`.parts/` 里长度对的片不重下）。
- 想一口气下完就别让电脑睡；也可以分多次跑，工具有幂等性的，不会重复劳动。

## 5. 程序（要改代码看这里）

- `program/` 只是**只读快照**，由 `tools/sync_program.sh` 从 43 取回，用于"本地代码 = 线上代码"的可验证性。
  它与仓库根目录的 `recorder_l2_dual.py` 内容通常一致；**两者不一致 = 线上有未入库的改动**，这就是漂移证据。
- **可编辑源码**：
  - 采集器：仓库根目录 `recorder_l2_dual.py` / `watchdog_l2.sh`（本仓库，GitHub `wietrade/Polymarket-L2`）→ 改动经该仓库推上 43。
  - 打包/发布脚本：`polymarket-l2/tools/l2_pack*.py|sh`（随 **polymarket-l2** 仓库版本化，不再由 updown-live 分发）。

> 为什么一定要先在仓库提交再部署：2026-09-10 的 `sub_gen` 热修一度处于
> 「线上在跑、本地有、仓库没有」的状态，一旦本地丢失修复就没了。

## 6. 已知坑（都是踩过的，研究时注意）

| 坑 | 说明 |
|:---|:---|
| **单连接被限速** | 43 本机从 8001 下载 323 MB/s、服务器到国际 1.09 MB/s、本机到 Cloudflare 482 KB/s，但**43↔本机单连接只有 9~30 KB/s**；实测 8 并发 93 KB/s、24 并发 173 KB/s ⇒ 用 `--jobs` 绕开 |
| **同名重打** | 见 §4；必须比 sha256 |
| **文件名 ≠ 市场** | 单个 `<slug>.jsonl.gz` 里可能混入相邻轮次/别的市场的行 ⇒ 一律**按每行的 `asset_id`/`market` 字段归因**，别看文件名。派生层已把这件事做完（`is_primary` 列标出哪些行不是本文件主市场）|
| **历史数据的时间覆盖** | 2026-09-10 之前，采集器在每 bar 前 ~120s 是瞎的（切 bar 后旧连接上发订阅帧不生效）；已于 09-10 16:51 用「订阅代 `sub_gen`」修复 ⇒ **09-10 08:51 UTC 之前的数据只应信任每 bar 末 ~180s**（该时点之后已实测正常，见下），涉及 bar 前段的研究口径需重跑。量化工具：`tools/l2_bar_coverage.py` |
| **当天日包不完整** | 打包 cron 03:30（北京）跑时该 UTC 日还没过完 ⇒ 当天包只覆盖到 UTC ~19:30（例：09-10 包缺最后 ~4.5h，且含 1 个“还在写入就被打包”而截断的文件）。次日重打后 `python tools/l2_get.py` 会按 sha256 发现变化并重下 |
| **ssh 会吞 stdin** | 脚本里循环 `while read ... done <<< "$list"` 时，`ssh` 必须加 `-n`，否则它吃掉剩余输入、每轮只处理一个文件（`sync_program.sh` 踩过） |
| **watchdog 双写** | 历史上 watchdog 误重启旧版采集器，导致两个进程写同一批 gz ⇒ 文件交错损坏。现在 watchdog 只认 `recorder_l2_dual.py` 单例（锁口 45614） |

### 已验证：`sub_gen` 修复确实生效（2026-09-11 用本地数据实测）

修复点在 **2026-09-10 08:51 UTC**（北京 16:51），正好落在 09-10 这一天内 ⇒ 可做**同日前后对比**。
工具 `tools/l2_bar_coverage.py`，按每行自己的 `market` 字段归因（不看文件名、不看文件头几行）：

| 时段 | 线 | bars | 首帧 p50 | 首帧 p90 | 覆盖秒数 p50 | 首帧 >90s |
|:--|:--|--:|--:|--:|--:|--:|
| 修复前（09-09 全天对照） | btc 5m | 287 | 124.9s | 156.0s | 169.5s | 84.3% |
| 修复前 | eth 5m | 281 | 124.8s | 156.1s | 143.2s | 85.4% |
| 修复前 | btc / eth 15m | 96 / 96 | 126.6 / 126.4s | 349.3 / 305.0s | 745.6 / 732.5s | 96.9% |
| **修复后**（09-10 ≥08:51Z） | btc 5m | 127 | **5.5s** | 13.2s | **281.3s** | 1.6% |
| **修复后** | eth 5m | 127 | **5.8s** | 13.2s | **270.3s** | 1.6% |
| **修复后** | btc / eth 15m | 41 / 42 | **4.2 / 4.6s** | 13.7 / 13.6s | **847.4 / 845.3s** | 4.8% |

- 首帧偏移 **125s → 5.5s**；5m 覆盖 **170s → 281s**（满 300s 的 94%）；15m 覆盖 **746s → 847s**（满 900s 的 94%）
- 残余：每条线仍有 ~2 个 bar 首帧 >90s（1.6%，个别连接抖动，非系统性）
- ⚠️ **修复后 p90 仍是 13.2s** ⇒ 每 bar 开头 **bar+0~13s 仍有一段小空窗**；若研究/决策点落在 bar+15s 以内，需单独确认那几个 bar
