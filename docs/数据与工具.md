# L2 数据与工具（Polymarket updown 5m / 15m）

本仓库既是**采集器源码库**，也是**本地 L2 数据工作区**：把 43 上自研 recorder 采集的原始数据
按天取回本地，配套下载/校验工具，以及"线上正在跑的那份程序"的只读快照。

> 采集器本身的设计、参数、部署与运维见仓库根目录的 [`README.md`](../README.md)。

> 数据红线：`data/` 下的原始数据**勿删**。确需清理请先与负责人确认。
> 代码与数据分开（靠子目录，不靠两个仓库）：源码在仓库根，数据在 `data/`，工具在 `tools/`，线上快照在 `program/`。

## 2. 数据来源与发布链路

```
43 采集：polymarket-l2/recorder_l2_dual.py
        4 条线 = btc/eth × 5m/15m；每条线 2 条独立 WS 订同一市场（双连接热备，
        单条断线由另一条补，gap 归零）→ 去重 → 单文件模型写 gzip
        ↓ 落盘 /www/wwwroot/polymarket-l2/l2_data/<date>/*.jsonl.gz
打包/发布：**手工触发**（2026-09-12 复核：43 的 crontab 里已没有这条定时任务，见下）
        bash tools/l2_pack_publish.sh      # 在 43 的 /www/wwwroot/polymarket-l2/ 下跑
        l2_pack.py   按天打包（幂等；**当天的包会随数据增长被同名重打**）
        发布到 `<api 的 --www>/_dl/`（43 = /www/wwwroot/ts_test/www/_dl/；只服务扁平文件名）
        同时生成 _dl/manifest.json（文件名 + 大小 + mtime + sha256）
        ↓
本地：python tools/l2_get.py     （按清单只补缺的/变化的，校验通过才解压）
```

⚠️ **发布链路的现状（2026-09-12 复核，别照旧假设）**：
- **定时任务不在了**：43 root crontab 里只剩 `watchdog_l2.sh` 与 `watchdog_exp8867_loop.sh` 两条；
  `/etc/cron.d`、`/var/spool/cron` 里也没有 `l2_pack`。此前文档写的"每天 03:30 cron 自动跑"**已不成立** ——
  现在靠**手工跑**（实测当日 `_dl` 两次刷新 12:04 / 20:36 均非定时触发）。
- **发布目标没变**：仍是 `/www/wwwroot/ts_test/www/_dl/`（8001 的 `/dl/` 根，= api 的 `--www` 加 `_dl`），
  脚本里是写死的：`l2_pack_publish.sh` 的 `DL=$TS/www/_dl`、`l2_pack.py` 的 `DL = pathlib.Path("/www/wwwroot/ts_test/www/_dl")`。
- **执行者换了**：发布脚本现住 `/www/wwwroot/polymarket-l2/tools/`（本仓库的本地副本在 `program/pack/`，是**只读快照**）；
  `_dl/README.txt`（09-11）说的"本项目不再打包发布"指的是 `ts_test` 侧脚本已删，**不是**这个目录废弃。

数据内容：每个 `<date>/<coin>-updown-<cycle>-<epoch>.jsonl.gz` 是该 bar 的
`book`（L2 盘口增量）与 `last_trade`（真实成交）事件流。

### 当天数据：复核前必做（否则**静默**漏掉最新几小时）

发布链路有**两个"不自动"**，任何"用 L2 复核今天的成交/盘口"的任务都得先补上：

- 43 侧的打包**现在是手工触发**（2026-09-12 复核：crontab 里已无 03:30 这条定时任务，见 §2）
  ⇒ `_dl/` 里当天的包停在**上一次手工打包**的时刻；
- 本地 `data/derived/` 是**按需派生**的 ⇒ 没有新原始数据就不会自己更新。

2026-09-12 实测后果：派生层停在 **12:04**、原始采集一直在写（进程存活、心跳正常），
于是 12:04 之后的成交"核不了" —— 一次口径核对里有 **703/799 笔**都属于这一类，
**不是市场没数据，是本地的数据没补**。这类漏检如果只看"无法对齐 N 笔"的总数，是看不出来的
（updown-live 的 `ops/tools/spread_caliber_check.py` 现在会打印覆盖窗口并拆成"覆盖外/覆盖内"两类）。

```bash
# ① 43：重打当天包并发布到 8001/_dl（幂等，按 mtime 判增量；几秒~几分钟）
ssh -i <key> root@43.165.167.132 "cd /www/wwwroot/polymarket-l2 && bash tools/l2_pack_publish.sh"
# ② 本地：按清单补拉（sha256 校验通过才解压；合并式解压，会刷新被追加写过的老文件）
cd <polymarket-l2> && python -B tools/l2_get.py --include-today --jobs 24
# ③ 本地：重新派生（断点续跑）
python -B tools/l2_derive.py --days <date>
```

体量参考（2026-09-12）：当天包 21.9MB（12:04 那次）→ **71.7MB**（20:36 重打后）。
**别用 ssh+tar / 逐文件 scp 直接拉原始 gz** —— 实测聚合只有 ~6~20KB/s、单个文件握手就要 8s；
设计路线就是"43 打包 → 8001 断点续传（单连接限速，靠 `--jobs` 提速）"。

## 3. 常用命令

```bash
# 看清单与本地状态（不下载）
python tools/l2_get.py --list

# 补拉所有"已完成"的日包并解压（默认数据根 = ./data）
python tools/l2_get.py

# 并发数（默认 12）：本机到 43 单连接被限速，加大并发能明显提速
python tools/l2_get.py --jobs 24

# 只关心最近 3 天 / 只下不解压
python tools/l2_get.py --days 3
python tools/l2_get.py --no-extract

# 连当天的包也拉（当天还会变，慎用）
python tools/l2_get.py --include-today

# 手工下载单个包（curl -C - 续传）
curl -C - -O http://43.165.167.132:8001/dl/l2_2026-09-08.tar.gz
sha256sum -c l2_2026-09-08.tar.gz.sha256

# 核对本地程序快照是否与 43 运行版一致
bash tools/sync_program.sh --check

# 每 bar 覆盖率：首帧偏移 + 覆盖秒数（判断 recorder 有没有在录 / 某批数据能用在 bar 第几秒之后）
python tools/l2_bar_coverage.py --date 2026-09-10 --by-hour
python tools/l2_bar_coverage.py --date 2026-09-09 --date 2026-09-10 --detail

# 派生层：原始 gz → 可查询表（侧别映射 + 顶档/成交/gap），= 上面那几个坑的现成解法
python -B tools/l2_derive.py --self-test   # 离线自检（不联网、不碰真数据）
python -B tools/l2_derive.py               # 全流程（断点续跑）；口径见 docs/派生表-口径.md
```

## 4. 校验与对账

- **下载后必须看 sha256**：`l2_get.py` 会自动比对，不一致就不解压。
- **不要用"文件存在"判断已下载**：同一天的包会被**同名重打**（例如当天的包先只覆盖到
  某个时刻，之后再打一次才是完整版）。只判存在会永久漏掉后半天的数据。
- 程序快照对账：`program/VERSIONS.txt` 记录每个文件的 sha256，
  在 `program/` 下执行 `sha256sum -c VERSIONS.txt` 即可验证。

### 中断/休眠怎么办

- **电脑休眠会把本地下载冻住**（2026-09-11 实测：休眠后日志停在原地、进程也被清掉）；
  服务器侧不受影响（实盘、采录、打包 cron 照跑）。
- 醒来后**直接重跑 `python tools/l2_get.py` 即可**：
  已下完的包按 sha256 判为最新会跳过，下到一半的按分片续传（`.parts/` 里长度对的片不重下）。
- 想一口气下完就别让电脑睡；也可以分多次跑，工具有幂等性的，不会重复劳动。

## 6. 已知坑（都是踩过的，研究时注意）

| 坑 | 说明 |
|:---|:---|
| **单连接被限速** | 43 本机从 8001 下载 323 MB/s、服务器到国际 1.09 MB/s、本机到 Cloudflare 482 KB/s，但**43↔本机单连接只有 9~30 KB/s**；实测 8 并发 93 KB/s、24 并发 173 KB/s ⇒ 用 `--jobs` 绕开 |
| **同名重打** | 见 §4；必须比 sha256 |
| **文件名 ≠ 市场** | 单个 `<slug>.jsonl.gz` 里可能混入相邻轮次/别的市场的行 ⇒ 一律**按每行的 `asset_id`/`market` 字段归因**，别看文件名。派生层已把这件事做完（`is_primary` 列标出哪些行不是本文件主市场）|
| **深度是全档，但只有快照** | 原始 `book` 帧就是**服务端全量订单簿快照**（2026-09-14 全量扫描：最多 **155 档/侧**、**98.7%** 的帧覆盖到 0.01/0.99 两端）⇒ 需要任意档位**直接从原始 gz 取**（派生层只留顶档）。⚠️ 但采集端**丢弃 `price_change`/`tick_size_change`** 且按 `hash` 做 **60s 去重** ⇒ 存下来的是「变了才存的全量快照序列」，**帧间隔（p50 100ms）≠ 服务端推送频率**，子 ~100ms 的挂撤单不可见。审计工具 `tools/l2_depth_audit.py` |
| **历史数据的时间覆盖** | 2026-09-10 之前，采集器在每 bar 前 ~120s 是瞎的（切 bar 后旧连接上发订阅帧不生效）；已于 09-10 16:51 用「订阅代 `sub_gen`」修复 ⇒ **09-10 08:51 UTC 之前的数据只应信任每 bar 末 ~180s**（该时点之后已实测正常，见下），涉及 bar 前段的研究口径需重跑。量化工具：`tools/l2_bar_coverage.py` |
| **当天日包不完整** | 历史上由 cron 03:30（北京）打包，那时该 UTC 日还没过完 ⇒ 当天包只覆盖到 UTC ~19:30（例：09-10 包缺最后 ~4.5h，且含 1 个“还在写入就被打包”而截断的文件）。**2026-09-12 起该 cron 已不在**，改为手工重打；重打后 `python tools/l2_get.py` 会按 sha256 发现变化并重下 |
| **ssh 会吞 stdin** | 脚本里循环 `while read ... done <<< "$list"` 时，`ssh` 必须加 `-n`，否则它吃掉剩余输入、每轮只处理一个文件（`sync_program.sh` 踩过） |
| **watchdog 双写** | 历史上 watchdog 误重启旧版采集器，导致两个进程写同一批 gz ⇒ 文件交错损坏。现在 watchdog 只认 `recorder_l2_dual.py` 单例（锁口 45614） |

### 已验证：深度完整性（2026-09-14 全量扫描，工具 `tools/l2_depth_audit.py`）

4219 个文件 / 726 万行 / **492.7 万** `book` 帧全量扫完（0 行 bad_json；读失败 8 个 = 当天正在写入的）：

| 维度 | 实测 | 判据 |
|:--|:--|:--|
| **档位数** | p50 46 ｜ p90 91 ｜ p99 **99** ｜ **max 155** 档/侧 | 无 top-N 截断（截断会在 20/50 这类整值堆叠）；155 来自处于 **0.001 tick 模式**的帧 |
| **覆盖两端** | 买侧含 0.01 的帧 **98.7%**；卖侧含 0.99 同 | 深度覆盖到网格两端 |
| **单侧空盘口** | 1.26%（62,159 帧） | bar 结算前后，正常 |
| **事件类型** | `book` 4,927,485 ｜ `last_trade_price` 2,332,771 ｜ **`price_change` = 0** | 采集端 `recorder_l2_dual.py:288` 主动 `continue` 丢弃 |
| **帧间隔** | 38.8% <50ms ｜ p50 **100ms** ｜ 1.0% 在 10~60s | 去重后口径，**非**服务端推送频率 |

**结论**：**档位维度是全量**（任意深度可直接取用）；**时间维度不是逐笔**（只有快照，增量流已丢）。

`price_change` 丢不丢要紧吗 —— 实测 **49.2 万对相邻帧**：相邻帧量没变的仅 **0.4%**、价没变的 68.4%、
变化 <1 tick（≈200bp@0.5）占 **69.0%** ⇒ 服务端每次盘口变化基本都被 `book` 快照收下，丢的只是「更早到达」（毫秒级），
**在我们关心的 200bp 尺度上可忽略**；且加落盘量有实证风险（v2 暴断真因就是写盘阻塞 recv → 1013 slow consumer）⇒ **不建议补增量**。

⚠️ **派生层只在本地**（43 上无 `derived/`、无 `l2_derive.py`；且 43 只有 **2 vCPU / 3.6 GB**，还跑着采集器与实盘）
⇒ 要加「深度派生」一律在本地做，43 的职责保持「采集 + 打包」。
